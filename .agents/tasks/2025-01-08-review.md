## Summary

The Interview MVP implements a complete end-to-end adaptive interview system: students configure interviews (job role, type, difficulty, question count), answer AI-generated questions one at a time, receive AI evaluations with rubric scoring, and view comprehensive performance reports. The implementation includes five backend services (interviews, questions, answers, evaluations, recommendations), three frontend pages (setup, room, report), full AI service integration with fallback strategies, and state machine enforcement.

The architecture is sound. Backend services properly separate concerns, AI integration uses robust fallback patterns, and frontend UX handles loading/error states well. Services perform ownership checks via `interview.userId === userId` before database operations, preventing unauthorized access.

**Watch for:** Missing @UseGuards(JwtAuthGuard) decorator on InterviewsController exposes all interview endpoints without JWT verification (**confirmed** - other controllers like ProfilesController use it, interviews does not). No retry logic in evaluateAnswer despite requirement for 3-attempt retry with fallback (**confirmed** - single fetch call with no retry loop). No explicit validation that AI response scores fall within 0-100 range before persisting to database (**confirmed** - evaluations.service.ts accepts AI scores without bounds checking). StudentProfile entity uses snake_case column names but questions.service.ts accesses properties as `profile?.technical_skills` which works because TypeORM entity defines them as snake_case properties (**not a bug**, but naming inconsistency between entity field naming and database column naming could cause confusion).

**Verdict**: NEEDS_CHANGES

## High-level view

The InterviewsController lacks the @UseGuards(JwtAuthGuard) decorator that other controllers use, leaving all interview endpoints unprotected at the route level despite userId being extracted from CurrentUser decorator — authorization depends entirely on service-layer ownership checks without JWT verification happening first.

The evaluateAnswer method in EvaluationsService makes a single fetch call to the AI service with no retry mechanism, falling back to heuristic scoring on any error, rather than implementing the required 3-attempt retry strategy before using fallback scores.

AI response scores from the evaluation endpoint are not validated before database persistence — if the AI service returns scores outside 0-100, they will be saved directly to the database, potentially corrupting aggregate calculations despite the service using heuristic defaults when AI is unavailable.

The startInterview method transitions status to IN_PROGRESS and saves immediately before generating the first question, so if question generation fails, the interview remains stuck in IN_PROGRESS rather than reverting to CREATED, blocking retry attempts.

The state machine enforcement prevents answering questions unless status is IN_PROGRESS and blocks starting completed interviews, but the lack of transaction boundaries means partial state updates can leave interviews in inconsistent states when operations fail mid-execution.

## Missing authentication guard on interview endpoints

The InterviewsController uses the `@CurrentUser()` decorator to extract `user.userId` in every method, but the controller class itself lacks the `@UseGuards(JwtAuthGuard)` decorator. Other controllers in the codebase (ProfilesController, ResumesController) apply the guard at the class level:

```typescript
@Controller('profile')
@UseGuards(JwtAuthGuard)  // ← Present in profiles controller
export class ProfilesController { ... }
```

The interviews controller omits this:

```typescript
@Controller('interviews')
// @UseGuards(JwtAuthGuard) ← MISSING
export class InterviewsController { ... }
```

Without the guard, NestJS does not verify the JWT token before route handler execution. The `@CurrentUser()` decorator will fail to extract userId (likely returning undefined), causing service methods to treat every request as unauthenticated. While service-layer ownership checks (`interview.userId !== userId`) would catch unauthorized access, they cannot execute properly if userId is undefined.

This is a **confirmed** security gap. Every interview endpoint (create, start, submit answer, get report, list interviews) is exposed without JWT verification. An attacker could potentially invoke these endpoints with forged or missing tokens.

The fix is straightforward: add `@UseGuards(JwtAuthGuard)` at the controller class level, matching the pattern used throughout the codebase.

## No retry mechanism in answer evaluation

The requirements specify: "Does evaluateAnswer retry 3 times and save fallback?" The implementation in `evaluations.service.ts` makes a single fetch call to the AI evaluation endpoint:

```typescript
try {
  const response = await fetch(`${this.aiServiceUrl}/evaluation/evaluate`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ ... }),
  });

  if (response.ok) {
    const data = await response.json();
    // parse AI scores
  }
} catch (err) {
  this.logger.warn(`AI evaluation endpoint unavailable, using rubric heuristic`);
}
```

If the fetch throws an exception (network timeout, DNS failure, service down), the catch block immediately falls back to heuristic scoring. There is no retry loop. A transient network glitch that would resolve on retry results in using fallback scores instead of the AI evaluation.

The correct implementation:

```typescript
let attempts = 0;
const maxRetries = 3;
let aiResponse = null;

while (attempts < maxRetries && !aiResponse) {
  try {
    const response = await fetch(...);
    if (response.ok) {
      aiResponse = await response.json();
      break;
    }
  } catch (err) {
    attempts++;
    if (attempts < maxRetries) {
      await new Promise(resolve => setTimeout(resolve, 1000 * attempts)); // exponential backoff
    }
  }
}

if (!aiResponse) {
  this.logger.warn(`AI evaluation failed after ${maxRetries} attempts, using fallback`);
  // use heuristic scores
}
```

**Confirmed** missing: no for-loop, no attempt counter, no retry logic present in evaluations.service.ts.

## AI response scores not validated before persistence

The `evaluateAnswer` method receives score breakdown from the AI service and directly assigns them:

```typescript
if (response.ok) {
  const data = await response.json();
  const bd = data.breakdown || {};
  accuracy = Number(bd.technical_accuracy) || accuracy;
  completeness = Number(bd.completeness) || completeness;
  clarity = Number(bd.clarity) || clarity;
  relevance = Number(bd.relevance) || relevance;
  feedback = data.detailed_feedback || feedback;
  strengths = data.strengths || strengths;
  weaknesses = data.areas_for_improvement || weaknesses;
}
```

If the AI service returns `technical_accuracy: 150` or `clarity: -20`, these values are coerced to numbers and used in the rubric calculation:

```typescript
const calculatedScore = Number(
  ((accuracy * 0.35) + (completeness * 0.30) + (clarity * 0.20) + (relevance * 0.15)).toFixed(2),
);
```

A score of 150 would inflate the aggregate score beyond 100. A negative score would deflate it below 0. The evaluation record is saved with these invalid scores, corrupting the overallScore calculation in recommendations.service.ts.

The fallback defaults (accuracy = 75, completeness = 70, etc.) are within bounds, so heuristic evaluation is safe. The vulnerability is specific to AI responses.

**Confirmed** gap: no `if (accuracy < 0 || accuracy > 100)` validation before using AI scores.

## Interview state not reverted on question generation failure

The `startInterview` method in interviews.service.ts performs state transitions before generating the first question:

```typescript
if (interview.status === InterviewStatus.CREATED) {
  interview.status = InterviewStatus.IN_PROGRESS;
  interview.startedAt = new Date();
  await this.interviewRepository.save(interview);  // ← Committed to DB
}

// Ensure first question is generated if no questions exist
let currentQuestion: InterviewQuestion | null = null;
if (!interview.questions || interview.questions.length === 0) {
  currentQuestion = await this.questionsService.generateNextQuestion(interviewId);  // ← Can throw
}
```

If `generateNextQuestion` throws an exception (AI service down, network timeout, database write failure), the exception propagates to the controller, which returns 500 to the client. But the interview record is already marked IN_PROGRESS in the database.

The state machine prevents re-starting an interview that's already IN_PROGRESS:

```typescript
if (interview.status === InterviewStatus.CREATED) { ... }
// If status is IN_PROGRESS, this block is skipped
```

A second call to `/interviews/:id/start` will skip the status transition and attempt to return the existing first question, but if no question was generated (because the first call failed), it returns `currentQuestion: null`. The frontend shows the interview room with no question to answer, and the student cannot proceed.

The fix: wrap question generation in try-catch and revert status to CREATED if generation fails:

```typescript
if (interview.status === InterviewStatus.CREATED) {
  interview.status = InterviewStatus.IN_PROGRESS;
  interview.startedAt = new Date();
  await this.interviewRepository.save(interview);
  
  try {
    currentQuestion = await this.questionsService.generateNextQuestion(interviewId);
  } catch (err) {
    // Revert to CREATED so user can retry
    interview.status = InterviewStatus.CREATED;
    interview.startedAt = null;
    await this.interviewRepository.save(interview);
    throw err;
  }
}
```

**Confirmed** issue: status committed before question generation, no rollback on failure.

## Multi-step operations lack transaction boundaries

Several service methods perform multiple database writes without transaction isolation:

**submitAnswer** (answers.service.ts):
1. Save answer record
2. Increment interview.answeredQuestions
3. Save interview record
4. Generate next question (inserts question record)
5. If finished, transition status to COMPLETED

If step 4 (generate next question) fails, steps 1-3 have already committed. The interview shows `answeredQuestions` incremented but no corresponding new question exists. Retrying the operation will fail because the answer already exists (checked earlier in the method).

**completeInterview** (interviews.service.ts):
1. Change status to COMPLETED
2. Set completedAt timestamp
3. Save interview record

This one is less critical (single entity update), but if the save fails, the method has no rollback logic.

**generateRecommendations** (recommendations.service.ts):
1. Fetch all answers
2. Generate evaluations for each answer (multiple AI calls)
3. Calculate aggregate score
4. Call AI for recommendations
5. Save/update recommendation record
6. Update interview.overallScore
7. Change interview.status to EVALUATED
8. Save interview record

If step 8 fails, steps 5-7 are in inconsistent state (recommendation record exists, but interview status is still COMPLETED, not EVALUATED).

TypeORM supports transactions via QueryRunner or the `@Transaction()` decorator. Wrapping these multi-step operations in transactions ensures atomicity:

```typescript
async submitAnswer(userId: string, interviewId: string, dto: SubmitAnswerDto) {
  return await this.answerRepository.manager.transaction(async (manager) => {
    // All operations use manager.save() instead of repository.save()
    const answer = manager.create(InterviewAnswer, { ... });
    await manager.save(answer);
    
    interview.answeredQuestions += 1;
    await manager.save(interview);
    
    const nextQuestion = await this.questionsService.generateNextQuestion(interviewId);
    // If this throws, transaction rolls back answer + interview update
    
    return { answer, nextQuestion };
  });
}
```

**Confirmed** gap: no transaction wrappers around multi-step database writes in submitAnswer, generateRecommendations, or startInterview.

## StudentProfile property naming inconsistency

The StudentProfile entity defines database columns with snake_case names but TypeScript properties as snake_case identifiers (not camelCase):

```typescript
@Column({ type: 'uuid', unique: true })
user_id: string;  // ← Property name is snake_case

@Column({ type: 'text', array: true, nullable: true })
technical_skills: string[] | null;
```

The questions.service.ts accesses these properties as `profile?.technical_skills` and `profile?.experience_level`, which is correct because the entity properties are defined as snake_case. This is **not a bug** in the current code.

However, it creates a naming inconsistency: most other entities in the codebase use camelCase property names with `@Column({ name: 'snake_case' })` mappings. For example, Interview entity:

```typescript
@Column({ name: 'user_id' })
userId: string;  // ← Property is camelCase, column is snake_case
```

The StudentProfile entity should follow the same pattern to maintain consistency. This is a **non-blocking** style issue, not a functional defect. The current code works correctly, but future developers might expect `profile.userId` instead of `profile.user_id`, leading to confusion.

Recommendation: Refactor StudentProfile entity to use camelCase properties with explicit column mappings:

```typescript
@Column({ name: 'user_id', type: 'uuid', unique: true })
userId: string;

@Column({ name: 'technical_skills', type: 'text', array: true, nullable: true })
technicalSkills: string[] | null;
```

Then update questions.service.ts to use `profile?.technicalSkills` and `profile?.experienceLevel`. This change is purely stylistic and does not affect current functionality.

## What works well

**State machine enforcement:** The interviews.service.ts prevents invalid state transitions. Cannot start a COMPLETED interview, cannot answer questions unless IN_PROGRESS, cannot mark EVALUATED interviews as IN_PROGRESS. The logic in startInterview, submitAnswer, and completeInterview correctly guards against out-of-order operations.

**AI fallback strategies:** Every AI service integration (question generation, answer evaluation, recommendations) has a heuristic fallback when the AI service is unavailable. Questions fall back to generic role-specific questions. Evaluations fall back to length-based scoring. Recommendations fall back to score-bracket feedback templates. This ensures the system degrades gracefully rather than failing entirely when AI is down.

**Ownership checks in every service method:** Every service method that accesses an interview, answer, or question verifies `interview.userId === userId` before proceeding, throwing ForbiddenException if the check fails. This prevents Student A from accessing Student B's interviews by changing the ID in the URL. The checks are consistent across all five services.

**Frontend loading and error states:** All three frontend pages (setup, room, report) handle loading, error, and success states. Loading screens show spinners with descriptive text. Errors display alert banners with actionable messages. The interview room page handles the finished state by showing a completion card with navigation options.

**Backend-controlled score calculation:** The evaluations.service.ts calculates the final score using the rubric formula (35% accuracy, 30% completeness, 20% clarity, 15% relevance) in application code, not delegating this to the LLM. The recommendations.service.ts calculates overallScore as the average of all evaluation scores in the backend. This prevents prompt injection attacks where an adversarial student could manipulate the LLM into returning inflated scores.
